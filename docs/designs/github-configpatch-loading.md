# Design: Load ConfigPatches from a GitHub Repo

Generated by /office-hours on 2026-08-24
Branch: fix/artifact-per-file-upload
Repo: Jubblin/omni-headlamp-plugin
Status: APPROVED
Mode: Startup (Intrapreneurship)

## Problem Statement

Add the ability to pull Talos `ConfigPatch` files from a GitHub repository and apply them
to Omni clusters/machines through this plugin's existing UI, instead of hand-typing them
into `ConfigPatchDetail`'s edit box every time.

## Demand Evidence

The founder is the user: they are the one hand-editing `ConfigPatches` through the plugin's
UI today. Three concrete, compounding pains (confirmed, not hypothetical):
1. **Lost source of truth** — after editing in the UI, there's no record of who/why/what the
   intended value was.
2. **Copy-paste/typo risk** — hand-typing YAML into a textarea with no diff or validation
   before it goes live on a cluster.
3. **Repetition across clusters** — the same or near-identical patch has to be re-applied to
   multiple clusters/machines, one at a time, by hand.

The single strongest signal: *"I re-type the same patch repeatedly."* Applying a known-good
patch to a new cluster means re-finding and re-typing it every time — a specific, recurring
time cost, not a vague discomfort.

## Status Quo

Hand-copy into the UI. There is no CLI or automation bypass today. Critically: **there is no
repo at all right now** — this isn't a case of a repo drifting from the UI, it's that
`ConfigPatches.omni.sidero.dev` resources in Omni are currently the *only* record that
exists. No version control, no audit trail, no diff against a prior known-good value.

## Target User & Narrowest Wedge

Target user: the founder themselves ("it's me") — a solo operator, not a team persona.
Narrowest wedge: a **manual, human-triggered** "browse a GitHub repo → pick a file → diff
against the live ConfigPatch → apply" flow inside the plugin's existing UI. Not an
autonomous reconciling operator.

## Constraints

- Ships inside the existing plugin bundle (same `deploy/Dockerfile`, same release pipeline)
  — no new distribution channel.
- v1 is single-user — no team PR-review gate, no multi-approver workflow. Deferred, not
  blocking.
- Scope is `ConfigPatches` only (Talos machine/cluster-level config) — not `MachineClasses`
  or other Omni resource types.

## Premises

1. Scope is a manual, human-triggered browse→diff→apply flow — not an autonomous
   reconciling operator (Flux/ArgoCD-style). — **Agreed.**
2. Reuse two existing patterns rather than building new: `ResourceDetail.tsx`'s Monaco
   `DiffEditor` + trust-moment apply UX, and the paste-a-credential-into-`sessionStorage`
   pattern from `ConnectPrompt.tsx`/`auth.ts` — this time for a GitHub token. **Revised**
   after cross-model review: the token must be a **fine-grained, read-only, single-repo**
   PAT specifically, documented as such in the connect UI — not "any GitHub token." — **Agreed
   (revised).**
3. `ConfigPatches` only, not `MachineClasses` or other resource types. — **Agreed.**
4. Ships in the existing plugin bundle, no new distribution channel. — **Agreed.**
5. v1 is single-user; no PR-review/approval workflow yet. — **Agreed.**

## Cross-Model Perspective

Independent Claude subagent cold read (no visibility into this conversation):

- **Steelman**: "A one-person known-good ConfigPatch registry with recall — instead of
  re-deriving/re-typing a patch from memory each time, patches live in git with names and
  history, and applying one becomes a lookup-and-diff instead of a re-type-and-hope. A
  personal cache with an audit trail, wearing a GitOps costume."
- **Key insight**: the revealing line is *"I re-type the same patch repeatedly"* — the pain
  is retrieval, not reconciliation. That single sentence rules out watch-loops, controllers,
  or scheduled sync.
- **Challenged premise**: originally flagged premise 2 (sessionStorage reuse) as too loose —
  a GitHub PAT's blast radius (repo read, possibly org-wide) isn't the same risk class as
  Omni's session-scoped key, and re-pasting an unscoped token every session could reintroduce
  the exact copy-paste risk being solved for elsewhere. **Resolved**: premise 2 revised to
  require a fine-grained, read-only, single-repo PAT.
- **48-hour prototype suggestion**: `GET /repos/{owner}/{repo}/contents/{path}` for listing +
  fetch (base64-decode client-side, no clone/webhook); one new panel on
  `ConfigPatchDetail.tsx` feeding the existing `DiffEditor`; hardcode `main` (no ref
  selector); explicitly skip write-back to GitHub, batch-apply, and PR/commit-status
  creation for v1.

## Approaches Considered

### Approach A: Repo Browser Panel (chosen)
Add a "Load from GitHub" action on `ConfigPatchDetail` that opens a file picker fetched via
GitHub's Contents API, feeds the chosen file's content into the existing Monaco
`DiffEditor` against the live `spec.data`, and applies through the existing
apply/uncertain-apply flow, unchanged.
- Effort: S · Risk: Low
- Reuses `ResourceDetail.tsx`'s `DiffEditor` + apply flow, `ConnectPrompt.tsx`'s credential
  pattern, `client.ts`'s existing update path — entirely.
- **Decided for v1**: the Contents API call for a directory returns only its immediate
  children — "flat" means the picker lists just the files in that single response, filtered
  to `.yaml`/`.yml` extensions (ConfigPatch content is YAML), with a client-side text filter
  box on top. Any directory entries in the response are excluded from the list entirely (not
  shown, not clickable) — no expand/collapse UI to build. Fixed to the `main` branch (no ref
  selector). All scope cuts, not placeholders — see Premises.
- **Loaded content is a starting point, not a live sync**: once GitHub content is loaded into
  the diff editor, it behaves exactly like any other edit-in-progress in `ResourceDetail` —
  the user can still hand-edit before applying. This is a deliberate choice (matches the
  existing edit UX exactly, no new "locked" state to build) but means the "source of truth"
  premise only holds if the user applies what was loaded without further hand-editing. Worth
  restating to the user in the UI copy at load time.

### Approach B: New "GitHub Patches" Resource List
A first-class parallel list page mirroring `ConfigPatchesList`, showing every file in the
configured repo path, each row deep-linking into the diff-and-apply flow, plus multi-select
for batch-apply-to-multiple-clusters.
- Effort: L · Risk: Med
- Directly solves the "repetition across clusters" pain, but batch-apply orchestration
  (sequencing, partial-failure handling) is new logic with no existing pattern to lean on —
  real new risk, not reuse. Deferred as v2: prove the retrieval fix alone kills the retyping
  pain before adding batch orchestration.

### Approach C: GitHub Actions Workflow Trigger (rejected)
Plugin dispatches a GitHub Actions workflow that applies the patch via CI, using GitHub
Actions run history as the audit trail instead of an in-plugin diff.
- Rejected: directly contradicts agreed premise 1 (async trigger-and-wait, not "diff and
  apply right here"). Also introduces a CI workflow file in the target repo as new coupling
  this plugin doesn't control end to end.

## Recommended Approach

**Approach A.** Direct fix for the confirmed pain ("I re-type the same patch repeatedly"),
reuses the plugin's existing diff/apply trust-moment pattern instead of a new UI paradigm,
and matches the confirmed premise that this is a manual single-apply flow. Approach B's
batch-apply is a legitimate v2 once A proves the retrieval fix alone addresses the retyping
pain.

## Open Questions

**Decided:**
- Settings shape: one new field in `settings.tsx`, `githubPatchesPath`, a single string in
  the form `owner/repo` or `owner/repo/path/to/patches` (path segment optional — omitted
  means repo root). Parsed client-side by splitting on `/`: 0 or 1 segments is invalid input
  (show a validation error), the first segment is always `owner`, the second is always
  `repo`, and everything after the second `/` (if anything) is joined back together as
  `path` — unambiguous regardless of how many slashes the path itself contains, since GitHub
  owner/repo names can't contain `/`. Matches the existing single-`TextField`-per-setting
  pattern already used for the Omni endpoint field — no new settings UI paradigm.

**Non-blocking (can resolve during implementation):**
- Exact GitHub API auth surface: fine-grained PAT only for v1, or also support a GitHub App
  installation token later if this expands beyond solo use?
- PAT lifecycle: sessionStorage only (cleared on tab close, re-entered every session, same as
  the Omni service-account key today) — confirm this is acceptable rather than assumed by
  analogy.

## Error Handling & Failure Paths

Not covered by Success Criteria's happy path — must be handled, not deferred:
- **Invalid/expired PAT** or **repo access denied**: surface the same class of error banner
  `ConnectPrompt.tsx` already shows for a bad Omni service-account key.
- **File/repo not found (404)**, configured path doesn't exist, or zero `.yaml`/`.yml` files
  remain after filtering: picker shows the same empty state, not a silent failure.
- **Malformed content**: the fetched file isn't valid YAML, or doesn't look like a
  ConfigPatch. Since `ConfigPatchDetail`'s `parseEdit` already treats ConfigPatch text as
  "trivial always-valid" (a free-text field), a malformed file doesn't block loading it into
  the diff editor — but the diff itself becomes the validation moment before Apply, same as
  today's manual-edit path.
- **GitHub Contents API's 1MB file-size limit**: files larger than this need the Git Blobs
  API instead; out of scope for v1 — surface a clear "file too large" error rather than a
  cryptic API failure.
- **Rate limits**: 5000/hr authenticated is generous for a solo user's browse-and-fetch
  pattern, but a 403 rate-limit response should surface as a clear message, not a generic
  error. Distinguish from a plain 403 access-denied by checking for GitHub's
  `x-ratelimit-remaining: 0` response header (or the rate-limit-specific message body) —
  without this check, a rate-limited request looks identical to a bad-PAT/access-denied
  error to the user.
- **Malformed/corrupted base64 content** (critical — no test or handling covered this
  otherwise): wrap the decode step in `fetchFileContent` in a try/catch that surfaces a
  clear "couldn't read file content" error, same class as the other `fetchFileContent`
  error cases, rather than letting a decode failure propagate as an unhandled exception.

## Feasibility Note

This design assumes `api.github.com`'s Contents API supports CORS for authenticated
browser-JS requests (no backend proxy) — the "no new service dependency" premise depends on
this. Confirm with one real fetch (see Assignment) before committing to the no-proxy
approach; if CORS doesn't work as expected, the fallback is a thin proxy through this
plugin's own existing backend, not a redesign.

## Success Criteria

- Founder can select a file from a configured GitHub repo, see a real diff against the live
  `ConfigPatch`, and apply it — without leaving the plugin or hand-typing YAML.
- No regression to the existing manual-edit path in `ConfigPatchDetail` — GitHub loading is
  additive, not a replacement.
- Zero new distribution/CI surface: ships through the existing `deploy/Dockerfile` and
  release pipeline unchanged.

## Distribution Plan

No new distribution channel needed — ships as part of the existing plugin bundle via the
already-established `deploy/Dockerfile` + release pipeline (`.github/workflows/release.yml`,
`.github/workflows/publish-container.yml`).

## Dependencies

- A fine-grained, read-only, single-repo GitHub PAT (user-provided per session, per the
  revised premise 2) — no new secret infrastructure needed.
- GitHub's Contents API (`GET /repos/{owner}/{repo}/contents/{path}`) — public API, no new
  service dependency.

The post-load confirmation Alert is the direct fix for Approach A's line 105-110 ("worth restating to the user in the UI copy at load time") — that requirement now has a concrete home instead of being an intention with no UI.

**AI-slop/hard-rule check**: this is an App UI (admin/ops tool), not marketing — no hard-rejection patterns apply (no card grids, hero, or carousel in scope). One universal NEVER rule to hold explicitly: the filter box's `label` prop must be a real visible label ("Filter files"), not placeholder-only text — placeholder-as-only-label is a hard rule violation (label disappears once the user types, breaking scanability for exactly the kind of dense admin UI this is). No cards planned (a plain filterable list), which avoids the card-grid AI-slop pattern by construction.

**Accessibility & responsive**: build the file list from MUI's `List`/`ListItemButton` (not a hand-rolled `<div>` list) — gets keyboard navigation, focus management, and ARIA semantics for free, matching how this codebase relies entirely on MUI's built-in accessibility today (zero hand-written `aria-*` attributes exist anywhere in `src/omni/`). Responsive layout is explicitly out of scope for this feature, consistent with the rest of the plugin — no responsive breakpoints exist anywhere in this codebase (`ClusterCreate.tsx` uses a fixed `maxWidth: 640`), matching a desktop-only Kubernetes admin tool. Adding responsive design for one small feature while the page it lives on has none would be a new, inconsistent precedent.

**Dirty-diff re-open guard**: if the DiffEditor already has unsaved hand-edits when "Load from GitHub" is clicked again, show a confirm step first — "You have unsaved changes. Loading a new file will discard them. Continue?" — reusing the existing delete-confirm Dialog's visual pattern. Extends `ResourceDetail.tsx`'s existing dirty-state guard (currently only covers leaving the page) to this one additional discard path, preventing silent data loss of exactly the hand-edited content Approach A's own design depends on ("loaded content is a starting point, not a live sync").

## User Journey — First-Use Cold Start (from /plan-design-review, 2026-08-24)

The riskiest moment in this feature's journey: first click on "Load from GitHub" hits
the PAT dialog, and the user has to go create a fine-grained, read-only, single-repo PAT
on GitHub's own UI — genuinely non-trivial (multiple form fields, easy to over-scope) with
zero in-context help as originally planned. `ConnectPrompt.tsx`'s equivalent moment has
explicit help copy; this dialog didn't.

**Fix**: the PAT dialog's help copy includes a **pre-filled GitHub template link**, using
GitHub's real (confirmed via
[docs.github.com](https://docs.github.com/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#pre-filling-fine-grained-personal-access-token-details-using-url-parameters),
shipped [August 2025](https://github.blog/changelog/2025-08-26-template-urls-for-fine-grained-pats-and-updated-permissions-ui/))
template-URL feature:

```
https://github.com/settings/personal-access-tokens/new
  ?name=omni-headlamp-plugin
  &description=Read-only+access+for+ConfigPatch+loading
  &target_name={owner from githubPatchesPath}
  &contents=read
```

Pre-fills the token name, description, owner (`target_name`), and the `contents=read`
permission. **Not fully verified**: whether the single-repo selection itself (as opposed to
the owner) is also parameter-driven, or still requires a manual click in GitHub's own repo
picker even with this link — confirm during implementation; if repo selection is still
manual, the dialog copy should say so explicitly ("click the link, then select
`{repo}` from the list") rather than implying full pre-fill.

## Engineering Decisions (from /plan-eng-review, 2026-08-24)

- **PAT entry UI**: inline dialog shown on "Load from GitHub" click, only if no PAT is
  already in sessionStorage for this tab/session — not a new field on `ConnectPrompt.tsx`
  (would force GitHub credential entry on every session even for users who never load from
  GitHub).
- **PAT validation timing**: optimistic store on paste, zero live validation — matches
  `ConnectPrompt.tsx`'s existing precedent for the Omni key exactly (parse-only where
  structurally possible, real validation on first actual use). No new pattern introduced.
- **GitHub OAuth/App login**: explicitly considered and rejected for v1 — real new
  infrastructure (OAuth App registration, callback route, Device Flow decision) for a
  confirmed single-user case. Captured as a deferred TODO (`TODOS.md`) for if/when this
  feature gets a second real user.
- **Network mechanism**: direct browser `fetch()` to `api.github.com`, NOT routed through
  Headlamp's `ApiProxy` (the mechanism every other network call in this plugin uses, see
  `omniProxy.ts:85`). GitHub's Contents API is documented to support CORS
  (`Access-Control-Allow-Origin: *`), unlike Omni's self-signed/proxied endpoint — routing
  through `ApiProxy` would cost operators an extra `-proxy-urls` allowlist entry for no
  benefit. **Not yet independently verified** — this is exactly what the Assignment's
  pre-code check confirms; treat as "expected to work," not settled, until that check runs.
- **Settings persistence**: `githubPatchesPath` persists through the existing `ConfigStore`
  pattern (`settings.tsx`'s `OmniPluginConfig`) — same as the Omni endpoint field. Not a new
  persistence mechanism; it's non-secret config, so it belongs alongside every other setting
  in this plugin, not in `localStorage` or anywhere else.
- **Test mocking strategy**: mock global `fetch` directly in `github.ts`'s tests — no
  injectable client wrapper. The module has exactly two API calls; an abstraction layer
  purely for testability would be premature for this size.

## Outside Voice (Cross-Model Review, /plan-eng-review, 2026-08-24)

An independent Claude subagent challenged this plan with no visibility into prior sessions.
Its strongest point: `ResourceDetail.tsx`'s Monaco `DiffEditor` already lets a user paste
GitHub content and see a diff before applying — so the delta this feature adds over
copy-paste-from-a-tab is convenience (skip the tab switch, get a picker), not the "lost
source of truth" fix the doc's framing implies. **Reviewed and the founder confirmed this is
still a real gap, not just convenience** — proceeding as designed. Six smaller gaps it found
were fixed directly in this doc: the CORS-confirmed/Assignment-still-verifies contradiction,
the missing Headlamp-CSP verification step, and the unspecified settings-persistence
mechanism. Two more were evaluated and explicitly kept as-is: the flat (non-recursive)
picker (kept — nested browse was already deliberately cut twice), and PAT lifecycle (kept
sessionStorage-only, matching the Omni-key precedent, with longer-lived storage captured as
a TODO instead of blocking v1). One point (review-process cost vs. an "Effort: S" build) was
noted but doesn't change anything — the review happened once, not on a growing formal cadence.

## The Assignment

Before writing any code: manually fetch one real ConfigPatch-shaped `.yaml` file from
GitHub's Contents API — from **inside a real Headlamp plugin context** (not a standalone
scratch script), using a plain `fetch()` call, not curl, to confirm CORS actually works from
browser JS *and* that Headlamp's own plugin CSP doesn't independently block the outbound
request (a `connect-src` restriction would fail this regardless of GitHub's CORS headers,
and the design's whole no-`ApiProxy` decision rests on this working). Also confirms the
base64-decode and directory-vs-file response-shape assumptions hold against a real repo.
15 minutes, catches both API and platform surprises before they're baked into a component.
